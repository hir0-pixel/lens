# RAG Production Implementation Report

Status: **Code-complete for the remaining in-repo RAG/model execution authorities; still NOT physical-production-ready.** Prior passes fixed authorization-first ordering, signed route policy, typed receipts, durable Cost/Agent-run libraries, and fail-closed profiles. **This pass** added deployable internal HTTP services and production `main()` clients for Model-use, Cost, Agent-run (including the shared claim store), signed Scheduler leases, retrieval sub-envelope accounting, signed Doc 014 workflow profile digests, and the Doc 012 `RuntimeAttemptStore` on the Model Gateway → runtime-adapter sidecar path. Production Orchestrator `main()` constructs those HTTP clients from environment configuration and no longer requires programmatic injection. Physical production remains **NO-GO** until real infrastructure load, security, zero-egress, failover and recovery evidence in §4 passes.

## 1. Canonical flow

```text
Browser UI
  -> BFF /api/rag/ask (live IdP introspection, CSRF, opaque conversation reference)
  -> Orchestrator /v1/chat (workload auth + short-lived request-bound assertion)
  -> live retrieval authorization and retrieval service
  -> internal model runtime
  -> Authority: admission, fences, encrypted output blob, disclosure authorization
  -> Memory Service: beginTurn before inference; finalizeTurn with exact output/evidence
  -> terminal commit only after Memory finalization
  -> BFF returns COMPLETED only after the complete release path succeeds
```

`COMPLETED` is not returned when Memory begin/finalize, output durability, Authority release, or terminal commit fails.

## 3. Implemented and verified

### Security and identity

- Delegated assertions use Ed25519: only the BFF holds private signing keys; Orchestrator and Memory receive audience-specific public verification keys. There is no production HMAC/shared-secret assertion fallback.
- The BFF uses distinct private-key profiles for `BFF_ASSERTION_PRIVATE_KEY` and `MEMORY_ASSERTION_PRIVATE_KEY`; Orchestrator verifies with `LENS_ORCHESTRATOR_ASSERTION_PUBLIC_KEY` and Memory verifies with its own audience-specific public key.
- Assertions are short-lived, versioned, canonical-base64url encoded, constant-time verified, and bound to issuer, audience, request, subject, session, device, conversation, and query digest.
- Conversation references are opaque, versioned, subject-bound, length-bounded, tamper-detected, and have no unsigned fallback.
- Production configuration rejects missing or reused signing material and requires separate BFF-to-Orchestrator and BFF-to-Memory private/public key profiles. Conversation references remain BFF-only HMAC.
- The browser does not use `session_ref` as `conversation_ref`; stable ownership is `(subject_ref, conversation_ref)` and survives session rotation.

### Memory turn lifecycle

- `ConversationHistoryPort.beginTurn` is called before router/model inference.
- `finalizeTurn` records the exact input digest, output, output digest, and terminal evidence.
- Terminal Authority commit happens only after Memory finalization succeeds.
- The in-memory and encrypted SQLite adapters emulate the same idempotent lifecycle for development/test only.
- Production Orchestrator startup constructs a bounded, deadline-controlled Memory HTTP client from `LENS_MEMORY_URL` and `LENS_MEMORY_WORKLOAD_TOKEN`; it does not construct a production SQLite history store.
- Every Memory get/begin/finalize request carries `request_id`, `subject_ref`, `session_ref`, `device_ref`, `conversation_ref`, `query_digest`, operation fields, and the audience=`memory` assertion; Orchestrator verifies both audience proofs before invoking the service.
- SQLite history is explicitly development/test-only. Shared paths and SQLite WAL are not treated as cross-host HA.

### Authority storage and output protection

- Authority store I/O is Promise-based behind `AuthorityStorePort`.
- SQLite is an async dev/test adapter and rejects legacy plaintext output schemas.
- Output blobs use AES-256-GCM with a required 32-byte key, unique nonce, authentication tag, digest verification, idempotency, and fail-closed wrong-key/tamper behavior.
- Production Authority startup rejects local SQLite and rejects startup unless deployer-supplied replicated storage, Governance, PDP, and readiness adapters are present. The local in-process governance ledger is never accepted as production authority.
- Production Authority also requires a Doc 005-backed `ProductionOutputDisclosureAuthorizationPort` and a Doc 021 quorum-backed `ProductionAuditAdmissionPort`, each with readiness. Local release-fence and audit-receipt creation is dev/test-only.

### Ownership gap

The repository's Authority service is a facade/coordinator. Production still requires deployer-supplied delegation for the authoritative Memory turn/output lifecycle and replicated output/terminal-state storage. The current SQLite output-blob and terminal-commit tables are development/test adapters, not the Doc 008 durable truth. No production claim is made for those local tables.

### Adaptive RAG routing and grounding-policy enforcement (Doc 004 §23)

Two correction passes. The first (see git history) removed `PermissiveGroundingPolicyPort`, moved policy resolution before the router, and implemented the Doc 004 §23 wire schema and grounding-required enforcement. The second — this pass — was told explicitly that several items the first pass reported as "scope notes" were unacceptable and had to be fixed for real or rejected at runtime, not deferred again. Result: 5 of 8 items are implemented for real; 2 are not implemented and are named in §3a with no softening; 1 (`MULTI_RETRIEVAL`) is handled by rejecting it at runtime, which was the user's own sanctioned fallback when full implementation isn't achievable in-pass.

**A pre-existing signature defect, found and fixed this pass:** `groundingPolicy.ts`'s `canonicalJson` was `JSON.stringify(value, Object.keys(value).sort())`. The second argument to `JSON.stringify` is a replacer *array*, which filters keys at **every** nesting level, not just the top — for a manifest shaped `{entries: [...]}`, the replacer is `["entries"]`, so every entry object (whose own keys are never named `"entries"`) canonicalized to `{}`. The HMAC signature therefore covered only the entry *count*: `groundingRequired`, `routerModelRef`, `defaultProfileSelector`, or any other entry field could be changed post-signing and the same signature would still verify. This was live in code shipped in the first pass. Fixed with a real recursive, key-order-independent canonicalizer; `routePolicyProductionWiring.test.ts` now has a same-key content-tamper test that fails under the old canonicalizer and passes under the new one.

**Implemented and verified this pass:**

- **MULTI_RETRIEVAL rejected as unsupported, not silently remapped.** The first pass mapped `MULTI_RETRIEVAL` onto the same single-retrieval call as `SINGLE_RETRIEVAL` while claiming the distinction was "preserved for audit" — exactly the "mapped onto different semantics" pattern the user forbade. `router.ts`'s `classifyTurn` now returns `failClosed: {reason: "multi_retrieval_unsupported"}` for any `MULTI_RETRIEVAL` result (router-attempted or policy-enforced), which `service.ts` turns into a `DENIED` response before Retrieval is ever called. The router prompt's advertised JSON schema no longer offers `MULTI_RETRIEVAL` as a choice, so a real model is not steered toward a route that can only ever be denied. Bounded multi-query fan-out itself (concurrency limits, per-candidate live authorization, dedup/fusion, citation lineage) is not implemented — production correctly refuses to claim it happened.
- **`workspace_ref`, `request_class`, and `purpose_ref` are cryptographically bound into the signed delegated session assertion, never read from the request body.** `DEFAULT_WORKSPACE_REF` (an orchestrator-local literal, unchecked against anything) is deleted. `services/security/workspaceContext.ts` defines `LENS_WORKSPACE_REF`/`LENS_REQUEST_CLASS`/`LENS_PURPOSE_REF` as the single source of truth; the BFF (`server/src/routes/api.ts`) binds all three into the Ed25519-signed assertion it issues, and the Orchestrator (`orchestrator-service/src/http.ts`) verifies the assertion against these same constants — never against `record.workspace_ref`/`purpose_ref` from the JSON body — before setting `request.workspaceRef`/`purposeRef` for route-policy lookup. A forged/replayed assertion bound to a different workspace, request class, or purpose fails closed at `sessionAssertionVerifier.verify()`, proven directly (`http.test.ts`, `security-bindings.test.ts`). **Caveat, stated as fact not hedge:** these three values are single-tenant literal constants — there is still no dynamic multi-workspace resolution anywhere in the codebase. What changed is that the constant is now cryptographically attested by the BFF and checked by the Orchestrator, not that workspace routing became dynamic.
- **Boot and readiness enumerate every live `router_model_ref` and validate it against Registry eligibility, including capability-specific approval.** `main.ts`'s `checkRoutePolicyModelsReady` (new) iterates `SignedRoutePolicyManifestPort.liveEntries()`, resolves each `router_model_ref` through the exact `modelSelection`/`modelEligibility` instances the service itself uses at request time, and additionally calls a new `RegistryModelGovernance.capabilityApproved()` accessor to confirm the resolved artifact is approved for `rag-route-classification` **specifically** — not merely routable for some other capability (final generation, say). Startup throws if any live scope's model fails; `/readyz` re-runs the same check on the existing 5s TTL, so a model revoked after boot degrades readiness without a restart. Proven with a real `ModelRegistry` (not a fake): unregistered alias, wrong-capability-but-otherwise-routable model, live revocation mid-process, and expired-scope-not-enumerated, each as a separate test (`routePolicyProductionWiring.test.ts`).
- **Route-override provenance is structured end to end on the Authority/audit side — no opaque string anywhere in that chain.** The first pass's audit admission carried only `{kind, requestId, turnId, inputDigest}`. It now carries a `routeOverride` object with all twelve fields the user named: `attemptedRoute`, `attemptedReasonCode`, `attemptedConfidenceBucket`, `attemptedProfileSelector`, `effectiveRoute`, `effectiveProfileSelector`, `groundingRequired`, `routePolicyRevision`, `routePolicyDigest`, `allowedProfileSetDigest`, `enforcementOverride`, `overrideReason`. This is real on the Authority side too, not just the Orchestrator's local type: `authority-service/src/service.ts`'s `AdmitInput`/`AdmitResult` carry the same fields, validated field-by-field (`assertRouteOverrideFields`), persisted in a new `route_override_json` column (with an `ALTER TABLE` migration for pre-existing dev databases), and idempotency now compares the full structured payload on retry — not just `inputDigest` — so a retry with different override provenance under the same `requestId` conflicts rather than silently returning the first receipt. Proven with a real HTTP round trip through a real `authority-service` instance (`authorityIntegration.test.ts`), not a fake port, plus 6 dedicated unit tests (`admissionRouteOverride.test.ts`). (The Memory-side `TerminalEvidence` object was, at the time, still collapsed to a single `routeOutput` + optional `routeOverride: {reason}` — completed to the full field set this pass; see §3b.)
- **Route-policy hot-reload is a bounded, in-process operation, not a restart, and prefers asymmetric verification.** `SignedRoutePolicyManifestPort` gained `reload(manifest, signature)`: re-verifies the signature, and additionally rejects rollback and duplicate/replayed revisions (the new manifest's `manifestRevision` must strictly exceed the current one) and rejects a manifest with zero live entries — on any rejection the previously-verified manifest stays in effect untouched. `Ed25519RoutePolicyManifestVerifier` is new and holds only a public key; `main.ts` prefers it via `LENS_ROUTE_POLICY_VERIFY_KEY` when set. `main.ts` wires `reload()` to `SIGHUP` against a manifest/signature file pair (`LENS_ROUTE_POLICY_MANIFEST_PATH`/`_SIGNATURE_PATH`) — env vars are fixed at process start and cannot themselves change, so a real reload path has to read from something that can change on disk between requests. **Caveat, stated as fact:** the legacy symmetric `HmacRoutePolicyManifestSigner`/`LENS_ROUTE_POLICY_OPS_KEY` path still exists and is used whenever `LENS_ROUTE_POLICY_VERIFY_KEY` is unset — the user asked to "prefer" asymmetric, not exclusively require it, and removing the HMAC path outright would have broken ~18 existing tests for no correctness gain; but a deployment that never sets `LENS_ROUTE_POLICY_VERIFY_KEY` is still on the legacy path where the Orchestrator process holds key material capable of signing policy, not just verifying it.

## 3b. This pass — workflow ordering, structured turn lineage, bounded reason codes

The user identified, correctly and independently of anything named in §3a, that the production request order was architecturally invalid: router classification (a real model dispatch through `ModelGateway`) and Memory's `beginTurn`/history read both ran in `ProductionOrchestratorService.handleChat()` **before** `Orchestrator.execute()` was ever called — meaning before the top-level PDP `authorizeGenerate` check ran at all. Only what happened after `execute()` was gated by authorization; router dispatch and Memory begin/history were not.

**P0 — workflow order corrected.** `route`/`requireGroundedContext` are no longer input fields on `ChatRequest`; `OrchestratorDependencies` gained `reserveWorkflowBudget` and `classifyRoute` steps, and `Orchestrator.execute()` now runs, in order: `authorizeGenerate` → `beginTurn` → `reserveWorkflowBudget` → `beginAgentRun` → `classifyRoute` → (grounded routes only) `resolveContext`/`authorizeContextUse` → `admitAudit("generation")` → `generate`. `ProductionOrchestratorService.handleChat()` no longer does anything before calling `this.orchestrator.execute(...)` except stash the inbound request; Memory's history read/`beginTurn`, route-policy resolution, the router's real model dispatch, and the grounding-override audit admission all moved into the `beginTurn`/`classifyRoute` dependency implementations, which the Orchestrator only reaches after `authorizeGenerate` has succeeded. Proven directly: `tests/integration/m04-orchestrator.test.ts` asserts the exact dependency call order and that a denied `authorizeGenerate` produces zero further calls; a new `orchestrator-service/tests/orderingAuthorization.test.ts` proves the same claim against real `ProductionOrchestratorService` production wiring (not a dependency double) — a denied top-level authorization (empty `subjectRef`, expired deadline) leaves Memory's `get`/`beginTurn` and the router's `classify` completely uncalled, and when authorization succeeds, Memory's history read and `beginTurn` complete before the router runs.

Honest scope note carried into this fix, not hidden: `reserveWorkflowBudget` mints one reservation **reference** per turn ahead of every consumer (correcting cardinality and ordering), but does not itself pre-charge `CostController` — the actual ledger entry is created lazily by whichever dispatch validates against it first. Route classification still mints its own separate, independent, still-fabricated budget reference (`route-budget:${requestId}`) rather than drawing a sub-envelope from the workflow reservation — that remains item 1 of §3a, unchanged in substance, just no longer created before authorization.

**P1 — structured turn lineage completed on the Memory side.** `TerminalEvidence` (`orchestrator-service/src/conversationHistory.ts`) previously carried only `routePolicyRevision`, `routePolicyDigest`, `routeOutput`, and a collapsed `routeOverride?: {reason}`. It now carries all twelve named fields — `attemptedRoute`, `attemptedReasonCode`, `attemptedConfidenceBucket`, `attemptedProfileSelector`, `effectiveRoute`, `effectiveProfileSelector`, `groundingRequired`, `routePolicyRevision`, `routePolicyDigest`, `allowedProfileSetDigest`, `enforcementOverride`, `overrideReason` — on **every** finalized turn, not only overridden ones (`enforcementOverride: false` with `attemptedRoute === effectiveRoute` is itself a checkable "no override happened" statement, not an absence). `memoryClient.ts`'s wire validation and payload construction were updated to match field-for-field with the exact `attempted_*`/`effective_*`/`grounding_required`/`route_policy_*`/`allowed_profile_set_digest`/`enforcement_override`/`override_reason` names the user specified, and the shape deliberately mirrors `RouteOverrideAuditFields` on the Authority/audit side (§3, above) so the two durable records are cross-checkable field by field, as required. Proven in `routePolicyProductionWiring.test.ts`'s override-provenance test (asserts on the Memory-side `TerminalEvidence` fields directly, not a collapsed string) and `memoryClient.test.ts`.

**P1 — bounded router reason codes.** `router.ts` previously accepted any non-empty `reason_code` string from the router model verbatim. It now defines a versioned (`ROUTER_REASON_CODE_SET_VERSION = 1`), bounded `ROUTER_REASON_CODES` enum covering both model-attempted reasons and internal fallback/enforcement reasons; `parseRouterWireDecision` rejects any `reason_code` outside that set as a schema violation — exactly like an out-of-set `profile_selector` — falling back deterministically rather than passing an arbitrary model-generated string into Audit, lineage, or telemetry. The router prompt (`buildRouterPrompt` in `service.ts`) now enumerates the exact allowed values instead of the prior placeholder text `"<bounded reason enum>"`, so a real model has a documented, bounded target to hit.

**MULTI_RETRIEVAL — the four stated conditions, checked:** (1) absent from the production router prompt — true, unchanged; (2) an unexpected `MULTI_RETRIEVAL` response is rejected explicitly — true, unchanged, `classifyTurn` returns `failClosed: {reason: "multi_retrieval_unsupported"}`; (3) policy/capability metadata marks it unsupported — added this pass: `router.ts` now exports `SUPPORTED_ROUTE_OUTPUTS` (`NO_RETRIEVAL`/`SINGLE_RETRIEVAL`/`CLARIFY` only, `MULTI_RETRIEVAL` deliberately excluded), the single named source of truth `classifyTurn`'s rejection path checks against; (4) no readiness/product claim says it is implemented — true; this report has never claimed it and does not now.

**Tests added or extended this pass:** `tests/integration/m04-orchestrator.test.ts` (rewritten for the new dependency shape; added ordering-specific cases), `orchestrator-service/tests/orderingAuthorization.test.ts` (new, real production wiring), `router.test.ts`/`service.test.ts`/`multiReplica.test.ts`/`routePolicyProductionWiring.test.ts`/`routerWireIntegration.test.ts`/`memoryClient.test.ts` fixtures updated for the bounded reason-code enum and the expanded `TerminalEvidence` shape.

**Not attempted this pass — still exactly what §3a below says:** a real shared Cost authority with non-interchangeable sub-envelopes, real PDP `AuthorizeModelUse`, real Scheduler/Agent-step one-use fences, and cryptographic (not non-emptiness) validation in `ModelGateway`. ## 3d. This pass — deployable network authorities, workflow accounting, signed Scheduler leases, Doc 012 attempt durability

- **Network authorities.** `authority-service` now serves `AuthorizeGenerate`/`AuthorizeModelUse` (`/v1/model-use/*`) with a service-side Ed25519 signing key. Dedicated `cost-authority-service` and `agent-run-authority-service` expose the Cost and Agent-run ports over internal HTTP (workload token, bounded JSON, health/ready). Agent-run is the single claim/replay owner (`/v1/claims`); Model Gateway's production `ClaimStore` is that client, not a second authority. Production storage is PostgreSQL (`postgres://` / `postgresql://` internal hosts only) via `PostgresCostAuthority` / `PostgresAgentRunAuthority` / `PostgresClaimStore` / `PostgresPool`; SQLite remains development/test (`Sqlite*` and `SqlitePgCompatPool`).
- **Production `main()` wiring.** `orchestrator-service/src/main.ts` `loadSharedAuthorities` for `production` constructs `ModelUseAuthorityHttpClient`, `CostAuthorityHttpClient`, `AgentRunAuthorityHttpClient`, and `CompositeReceiptVerifier` from `LENS_*_URL`, workload tokens, and public verification keys. Callers are not required to inject adapters; injection remains only as a test override. `RuntimeAttemptHttpClient` is constructed against `LENS_MODEL_RUNTIME_URL` (the runtime-adapter sidecar). Missing authority URLs/keys fail closed at startup.
- **Workflow accounting.** `reserveWorkflowBudget` resolves the signed route policy first, sizes four non-interchangeable sub-envelopes from policy-owned `workflowLimits` (defaults: route 4096, retrieval 100, final_generation 8192, tool 4), and binds `workflowProfileDigest` = SHA-256 of the canonical Doc 014 profile (application, workspace, purpose, request class, deadline, reservation, route-policy revision/digest, allowed profile set, allowed step classes, limits). `beginAgentRun` uses that digest. Retrieval `consumeSubEnvelope`/`finalizeSubEnvelope` wrap every Retrieval execution; failure retains the reservation (no automatic credit). Route and final-generation consume bounded token estimates, not `maximumUnits=1`.
- **Scheduler leases.** `GpuScheduler` issues `purpose=scheduler_lease` Ed25519 receipts bound to reservation, request/turn/step, model_ref, artifact digest, endpoint generation, request digest, expiry, and monotonic fence (`revision`). `ModelGateway` verifies the lease token before runtime contact; a fabricated numeric fence or arbitrary string fails.
- **Doc 012 RuntimeAttemptStore.** `RelationalRuntimeAttemptStore` implements ACCEPTED_NOT_CONTACTED → CONTACT_INTENT_COMMITTED → RUNTIME_STARTED → STREAMING → terminal, plus NOT_STARTED (only from ACCEPTED_NOT_CONTACTED with contact_intent=0) and OUTCOME_UNKNOWN (unresolved CONTACT_INTENT_COMMITTED). At most one accepted attempt per `reservation_id`. `GetAttemptStatus` is store-backed. `OUTCOME_UNKNOWN` is never automatically replayed. The runtime-adapter sidecar owns the cell store and signs **locally measured** output (UTF-8 bytes/4), not runtime-reported token counts. It is the only path Model Gateway uses for scheduler/runtime (`InternalInferenceClient` → sidecar, not the internal runtime). This is not tokenizer/model-artifact metering. Crash injection between the two attempt writes is covered in `orchestrator-service/tests/productionAuthorities.test.ts`. Orchestrator `/readyz` probes the sidecar. Production `main()` requires `LENS_USAGE_RECEIPT_PUBLIC_KEY`; Cost finalize uses sidecar-signed usage when the signature verifies and otherwise retains the reserved units. Finalize never credits below already-consumed units.
- **Deployment.** `deploy/on-prem/rag/base/authorities.yaml` plus Orchestrator env for Cost/Agent-run/sidecar URLs, tokens, receipt public keys, and `LENS_USAGE_RECEIPT_PUBLIC_KEY`.

## 3e. This pass — PostgreSQL dialect, transactional Cost/Agent-run, lease-bound attempts, adapter metering, bounded NDJSON

Independent audit defects were implemented in-repo, not only documented:

- **`pg.Pool`.** `PostgresPool` uses the declared `pg` package (`createRequire("pg").Pool`) with `max`, `connectionTimeoutMillis`, `idleTimeoutMillis`, `statement_timeout`, `transaction`, `ready`, and `close`. Hosts must be loopback, `postgres`, or `*.internal`. Production Cost / Agent-run / sidecar `main()` refuse SQLite (`LENS_*_DB_PATH` forbidden when profile is production). SQLite remains `SqlitePgCompatPool` for development/test, sharing one connection per path so concurrent in-process replicas serialize writes. `LEAST`/`GREATEST` are the stored SQL; SQLite rewrites them to `MIN`/`MAX` and strips `FOR UPDATE`.
- **Cost transactions.** Reservation parent + four envelope inserts are one transaction; `afterReserveParent` crash rolls back. Consume locks the reservation, then idempotency lookup, increment, receipt insert. Finalize uses `LEAST(maximum_units, GREATEST(consumed_units, measured))` and never lowers consumed units. Close finalizes remaining OPEN envelopes then CLOSED.
- **Agent-run.** `beginAgentRun` and identical `reserveAgentStep` are idempotent under races; unique `(run_id, step_index)`; consume only from RESERVED; finalize only from CONSUMED; close rejected while any step is nonterminal.
- **RuntimeAttemptStore.** Lease bind stores fence, endpoint, generation, digest, expiry. Sidecar `bind-lease` and generate require a **signed** `lease_token` verified against the stored attempt, not Orchestrator-only numbers. Transitions are store-enforced (`transitionTo` / `completeWithUsage`). Contacted failures become `OUTCOME_UNKNOWN` (Gateway and sidecar). `reconcileExpired` moves stranded contacted states to `OUTCOME_UNKNOWN`. Sidecar generate persists measured usage + terminal in one store transaction on success/cancel/oversize; uncertain runtime errors call `markOutcomeUnknown`.
- **Usage authority.** Sidecar signs `measureOutputUnits` (Unicode word-like segments, cap 1e6), not runtime-reported tokens. Orchestrator `claimVerifiedUsage` compares the signed payload to independently known request/turn/step/artifact context and claims `usageEventId` once. Conservative Cost finalize remains when verification fails.
- **Streaming.** Sidecar `/v1/inference/generate` is NDJSON with a 64KiB accumulated-output cap and write backpressure (`drain`). OpenAI-compatible adapters stream SSE deltas. This is **internal generation streaming**. Employee-visible release is still the existing Authority/Memory path.
